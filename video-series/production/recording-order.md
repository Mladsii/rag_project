# Порядок первых выпусков про RAG

Формат серии: один помощник магазина одежды постепенно проходит путь от CSV до поиска по фото. В каждом выпуске сначала показываем задачу или ошибку, затем меняем ноутбук, запускаем нужные ячейки и подводим итог.

## Выпуск 1. Из карточек товаров в документы

**Цель:** понять, что именно система будет искать.

**Показать:** CSV, поля товара, ID и ссылку-источник. Затем один товар как обычный Python-словарь и текст, который станет документом.

**Добавить в ноутбук:**
1. Заголовок и описание учебных данных, происхождения и ограничений.
2. Загрузка CSV и проверка обязательных столбцов.
3. Подготовка списка документов: `id`, `title`, `source`, `category`, `text`.
4. Вывод количества товаров, категорий и одного документа целиком.

**Проговорить:** «RAG начинается не с модели. Сначала нужны документы, понятные ID и источник, чтобы потом показать, откуда взялся ответ».

**Финал:** данные подготовлены локально; эмбеддинги и запросы к API ещё не выполнялись.

## Выпуск 2. От текста к эмбеддингам

**Цель:** увидеть, как текст становится вектором.

**Показать:** полный текст одной карточки; пока считаем каждую карточку одним чанком — это baseline, а не утверждение об идеальном разбиении.

**Добавить в ноутбук:**
1. Безопасная проверка окружения и чтение ключа из локального `.env`; никогда не выводить значение ключа.
2. Подготовка списка чанков с `chunk_id`, `document_id`, текстом и метаданными.
3. Перед платной ячейкой показать число текстов и пример отправляемых данных.
4. Вызов Embeddings API пакетно.
5. Проверка количества векторов, формы матрицы, размерности и нескольких координат.

**Проговорить:** «Сейчас тексты карточек отправятся в API эмбеддингов. Ответ API — числа; один вектор соответствует одному чанку. Это ещё не поиск».

**Финал:** векторы есть, но пока только в памяти ноутбука.

## Выпуск 3. Первый поиск: вопрос → top-3

**Цель:** увидеть retrieval отдельно от генерации ответа.

**Добавить в ноутбук:**
1. Ввод вопроса пользователя.
2. Эмбеддинг вопроса той же моделью.
3. Косинусное сходство в NumPy.
4. Вывод top-3 с названием, ID, фрагментом, ссылкой и оценкой.
5. Возможность поменять вопрос и снова посмотреть выдачу.

**Проговорить:** «Поиск возвращает ближайшие фрагменты, а не гарантированно правильный ответ. 0.6 — это оценка сходства, не 60% вероятности».

**Финал:** вручную проверить, попал ли нужный товар в выдачу и подтверждают ли фрагменты условия вопроса.

## Выпуск 4. Ответ с опорой на найденные документы

**Цель:** добавить generation после retrieval и сохранить ссылки на источники.

**Добавить в ноутбук:**
1. Отдельно показать найденный контекст.
2. Собрать запрос: вопрос, контекст, правила ответа.
3. Перед платной ячейкой показать, какие фрагменты отправляются в Responses API.
4. Попросить модель использовать ID источников и признать недостаток сведений.
5. Проверить ссылки и каждое фактическое утверждение ответа вручную.

**Проговорить:** «Промпт задаёт правила, но не гарантирует, что модель не ошибётся. Поэтому отдельно проверяем поиск и отдельно — ответ».

**Финал:** минимальный полный RAG работает; затем можно показать его ошибки и улучшать retrieval.

## Правила записи и API

- Разрабатывать и выполнять ноутбук сначала вместе, не писать всю серию заранее.
- Перед записью перезапустить kernel и пройти нужные ячейки сверху вниз.
- API-ячейки явно помечать: что отправляется, какая модель вызывается, возможна ли оплата.
- Во время записи не показывать `.env`, ключи, терминальный вывод с секретами и личные данные.
- Не запускать повторно платную ячейку ради дубля, если результат уже получен; заранее продумать запись экрана.
- Сохранять промежуточные результаты поиска и ответов так, чтобы зритель видел каждый этап.

## Что пока не добавляем

В первых четырёх выпусках не нужны Qdrant, LangGraph и reranker. Сначала зритель видит механику NumPy-поиска и понимает, где именно в системе позже появятся эти компоненты.
